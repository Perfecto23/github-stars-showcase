# Weekly CI Data Refresh Feasibility

Date: 2026-07-07 Asia/Singapore.

## Research Objective And Scope

This note evaluates whether `github-stars-showcase` can update its generated data weekly through GitHub Actions CI, and covers feasibility, recommended workflow design, required secrets and permissions, schedule behavior, GitHub API constraints, failure modes, and an implementation plan. Scope is limited to this repo's current package/scripts/config plus primary documentation from GitHub Actions, GitHub REST API, `actions/checkout`, and pnpm.

## Feasibility

Feasible with moderate confidence, provided the workflow uses a user PAT-like secret for reading the user's starred repositories and the repository `GITHUB_TOKEN` only for committing generated data back. The local update path already exists as `pnpm run update`, and it runs `fetch-stars`, `analyze`, `generate-data`, then `build`; those scripts are declared in `package.json` and orchestrated by `scripts/update.ts`. Sources: `package.json:5-17`, `scripts/update.ts:3-21`.

The CI workflow should not rely on the auto-created Actions `GITHUB_TOKEN` for fetching the user's starred repositories. GitHub documents that `GITHUB_TOKEN` is a GitHub App installation access token scoped to the repository that contains the workflow, while the REST starred-repositories endpoint is "List repositories starred by the authenticated user" and requires user-level `Starring` read permission for fine-grained tokens. Sources: [GITHUB_TOKEN docs](https://docs.github.com/en/actions/concepts/security/github_token), [REST starring docs](https://docs.github.com/en/rest/activity/starring#list-repositories-starred-by-the-authenticated-user), `scripts/fetch-stars.ts:10-27`.

The current fetch script is CI-compatible if a secret is exposed as `GITHUB_TOKEN` for the update step: it first reads `process.env.GITHUB_TOKEN`, falls back to `gh auth token`, throws if neither exists, constructs Octokit with auth, and sends `X-GitHub-Api-Version: 2022-11-28`. Sources: `scripts/fetch-stars.ts:6-27`, `scripts/fetch-stars.ts:43-50`, [REST API version docs](https://docs.github.com/en/rest/about-the-rest-api/api-versions).

The generated files that should be committed are tracked data surfaces, while raw fetch data and failed batches are intentionally ignored. `.gitignore` ignores `data/stars-raw.json` and `data/failed-batch-*.json`, and documents `data/analyzed.json`, `data/github-lists-progress.json`, and `public/data/repos.json` as tracked data files. Sources: `.gitignore:13-22`, `scripts/analyze-repos.ts:281-306`, `scripts/generate-data.ts:91-100`.

## Recommended Workflow Design

Use one scheduled workflow with a manual trigger:

- Trigger: `workflow_dispatch` plus `schedule`, weekly at an off-hour minute such as `20 2 * * 2` UTC for Tuesday 10:20 Asia/Singapore, or use the documented timezone support if adopting GitHub's current timezone-aware schedule syntax. GitHub documents that scheduled workflows run on the latest commit on the default branch, default to UTC, can use POSIX cron, and have a minimum interval of five minutes. Sources: [GitHub schedule docs](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).
- Install: check out the repo, install pnpm through the official pnpm GitHub Actions recipe, use Node 24, and run `pnpm install`. pnpm documents a GitHub Actions setup using `actions/checkout`, `pnpm/action-setup`, `actions/setup-node` with `cache: "pnpm"`, and `pnpm install`; pnpm also enables frozen-lockfile behavior in CI when a lockfile exists. Sources: [pnpm CI docs](https://pnpm.io/continuous-integration#github-actions), [pnpm install docs](https://pnpm.io/cli/install#--frozen-lockfile), `pnpm-lock.yaml`, `package.json:23-47`.
- Refresh: run `pnpm run update` with step-level environment variables for the star-reading token and AI provider credentials. The local update script runs fetch, AI analysis, data generation, and build in sequence. Sources: `scripts/update.ts:3-21`, `scripts/fetch-stars.ts:10-27`, `scripts/analyze-repos.ts:37-59`.
- Validate: keep `pnpm run typecheck` as an explicit gate, and keep `pnpm run build` either through `pnpm run update` or as a separate post-refresh gate. The repo exposes `typecheck`, `lint`, `build`, and `update` scripts, and `next.config.js` configures static export with `output: 'export'`. Sources: `package.json:5-17`, `next.config.js:1-9`.
- Commit back: configure git as `github-actions[bot]`, stage only `data/analyzed.json` and `public/data/repos.json`, skip commit when there is no diff, and push with the repository `GITHUB_TOKEN`. The first-party `actions/checkout` README says checkout persists credentials for authenticated git commands by default and gives an official "Push a commit using the built-in token" example with bot name/email, `git add`, `git commit`, and `git push`. Sources: [`actions/checkout` README](https://github.com/actions/checkout/blob/main/README.md#push-a-commit-using-the-built-in-token), `.gitignore:13-22`.

Recommended policy: direct commit to the default branch is acceptable for this narrow generated-data workflow if branch protection permits it; otherwise use the same refresh job to create a branch and open a PR with first-party GitHub CLI/API commands. If another GitHub Actions workflow or GitHub Pages build must run after the data commit, do not rely on a push made with the repository `GITHUB_TOKEN`, because GitHub documents that most events caused by `GITHUB_TOKEN` do not create new workflow runs and that `GITHUB_TOKEN` commits do not trigger a GitHub Pages build. Source: [GITHUB_TOKEN docs](https://docs.github.com/en/actions/concepts/security/github_token).

## Required Secrets And Permissions

- `STARS_GITHUB_TOKEN` or equivalent repository secret: pass it to the refresh step as `GITHUB_TOKEN` because current code reads that exact env var. For fine-grained tokens, the starred-repositories endpoint documents `Starring` user permission with read access; the README endpoint documents `Contents` repository permission with read access for fine-grained token use. Sources: `scripts/fetch-stars.ts:10-27`, [REST starring docs](https://docs.github.com/en/rest/activity/starring#list-repositories-starred-by-the-authenticated-user), [REST README docs](https://docs.github.com/en/rest/repos/contents#get-a-repository-readme).
- AI secret: provide `AI_API_KEY` or the provider-specific key matching `AI_PROVIDER`; current code defaults `AI_PROVIDER` to `anthropic` and checks `AI_API_KEY`, then provider-specific env names such as `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GOOGLE_API_KEY`, `COHERE_API_KEY`, and `DEEPSEEK_API_KEY`. Sources: `scripts/analyze-repos.ts:37-59`, `.env.example:9-31`, `scripts/ai-providers.ts:141-179`.
- Repository write permission: set workflow/job `permissions: contents: write` for the commit-back step. GitHub documents that `permissions` controls `GITHUB_TOKEN` scopes, supports `contents: read|write|none`, and unspecified permissions become `none` when any permission is specified. Source: [workflow permissions docs](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions).
- Secret injection: pass secrets as step `env` values rather than hard-coding values. GitHub documents that secrets are exposed to actions through the `secrets` context as inputs or environment variables, that missing secrets evaluate to an empty string, and that non-secret sensitive values should be masked explicitly. Source: [GitHub Actions secrets docs](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets).

Do not set a workflow-wide `GITHUB_TOKEN` env var to the personal star token. Keep the personal token scoped to the refresh command so checkout and push continue using the repository token created for the job. This recommendation follows from the local script's `GITHUB_TOKEN` env lookup and GitHub's separate repository-scoped `GITHUB_TOKEN` behavior. Sources: `scripts/fetch-stars.ts:10-27`, [GITHUB_TOKEN docs](https://docs.github.com/en/actions/concepts/security/github_token).

## Schedule Behavior And Limitations

- Scheduled workflows only run when the workflow file exists on the default branch, and the scheduled run uses the latest commit on the default branch. Source: [GitHub schedule docs](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).
- GitHub documents POSIX cron scheduling, default UTC scheduling, optional IANA timezone support in the current schedule docs, and a shortest interval of once every five minutes. Source: [GitHub schedule docs](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).
- GitHub warns that scheduled workflows may be delayed during high-load periods, that high load includes the start of every hour, and that sufficiently high load can drop queued jobs; scheduling at a non-zero minute lowers that risk. Source: [GitHub schedule docs](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).
- In public repositories, scheduled workflows are automatically disabled after 60 days without repository activity. Source: [GitHub schedule docs](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).

## Token And API Constraints

- The star fetch uses `listReposStarredByAuthenticatedUser` with `per_page: 100`, `sort: "created"`, `direction: "desc"`, and media type `application/vnd.github.star+json`; GitHub documents `per_page` max 100, `sort` values `created`/`updated`, `direction` values `asc`/`desc`, and the star media type for returning `starred_at`. Sources: `scripts/fetch-stars.ts:87-98`, [REST starring docs](https://docs.github.com/en/rest/activity/starring#list-repositories-starred-by-the-authenticated-user).
- The script requests each repo README with `repos.getReadme`, decodes base64 content, truncates to 500 characters, and treats README failures as non-fatal. GitHub documents the README endpoint and `404 Resource not found`; local code catches README errors and leaves `readmePreview` empty. Sources: `scripts/fetch-stars.ts:110-122`, [REST README docs](https://docs.github.com/en/rest/repos/contents#get-a-repository-readme).
- The script paginates by incrementing `page` until an empty response and throws on page-level failures. GitHub documents REST pagination via `per_page` and `page` parameters for this endpoint. Sources: `scripts/fetch-stars.ts:81-145`, [REST starring docs](https://docs.github.com/en/rest/activity/starring#list-repositories-starred-by-the-authenticated-user).
- Authenticated REST requests with a user token generally have a 5,000 requests/hour primary rate limit, and GitHub exposes `x-ratelimit-limit`, `x-ratelimit-remaining`, `x-ratelimit-used`, and `x-ratelimit-reset` headers. Source: [REST rate-limit docs](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api).
- Secondary limits still apply: GitHub documents limits on concurrent requests, requests to one endpoint per minute, CPU time, excessive compute, and content creation. The current fetch loop is sequential but performs one README request per starred repository, so a large star list can still consume many REST `GET` points. Sources: `scripts/fetch-stars.ts:87-122`, [REST rate-limit docs](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api).
- The local code already sends `X-GitHub-Api-Version: 2022-11-28`; GitHub recommends specifying this header and states that requests without it default to `2022-11-28`, while unsupported versions return `410 Gone`. Sources: `scripts/fetch-stars.ts:8-9`, `scripts/fetch-stars.ts:43-50`, [REST API version docs](https://docs.github.com/en/rest/about-the-rest-api/api-versions).

## Failure Modes

- Missing or wrong star token: `fetch-stars.ts` throws when neither `GITHUB_TOKEN` nor `gh auth token` is available, and the starred endpoint documents authentication/authorization constraints. Sources: `scripts/fetch-stars.ts:10-27`, [REST starring docs](https://docs.github.com/en/rest/activity/starring#list-repositories-starred-by-the-authenticated-user).
- Token scope mismatch: repository `GITHUB_TOKEN` is repository-scoped, while the starred endpoint is user-scoped; using only the auto-created Actions token is not the right authentication boundary for a user's stars. Sources: [GITHUB_TOKEN docs](https://docs.github.com/en/actions/concepts/security/github_token), [REST starring docs](https://docs.github.com/en/rest/activity/starring#list-repositories-starred-by-the-authenticated-user).
- README gaps: README fetch errors are swallowed, so the workflow can succeed with empty `readmePreview` fields if README access fails or a repository has no README. Sources: `scripts/fetch-stars.ts:110-122`, [REST README docs](https://docs.github.com/en/rest/repos/contents#get-a-repository-readme).
- AI provider failure: provider creation fails when required AI keys are absent, and batch analysis failures write `data/failed-batch-*.json` but do not immediately exit the analyze loop. Sources: `scripts/analyze-repos.ts:91-111`, `scripts/analyze-repos.ts:266-289`.
- Incomplete analysis blocks publish by default: `generate-data.ts` throws if raw repos lack analysis unless `ALLOW_INCOMPLETE_DATA=1`, so the weekly workflow should leave that flag unset if completeness is required. Source: `scripts/generate-data.ts:39-63`.
- No-op update: if no new stars are found, `analyze-repos.ts` exits with success before writing new analysis, and the commit step should skip when `git diff --quiet` sees no tracked data changes. Sources: `scripts/analyze-repos.ts:248-258`, [`actions/checkout` README](https://github.com/actions/checkout/blob/main/README.md#push-a-commit-using-the-built-in-token).
- Schedule reliability: GitHub may delay or drop scheduled jobs during high load and may disable schedules in inactive public repos. Source: [GitHub schedule docs](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).
- Commit/deployment chaining: pushes made with the repository `GITHUB_TOKEN` do not trigger most other workflows and do not trigger GitHub Pages builds, so any GitHub-native deployment that must follow should run in the same workflow or use a different approved credential. Source: [GITHUB_TOKEN docs](https://docs.github.com/en/actions/concepts/security/github_token).

## Implementation Plan

1. Add one workflow file such as `.github/workflows/weekly-data-refresh.yml` with `workflow_dispatch` and weekly `schedule`, using an off-hour cron minute. Source: [GitHub schedule docs](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).
2. Configure repository secrets: `STARS_GITHUB_TOKEN` for user-star reads, plus `AI_API_KEY` or the provider-specific AI key and optional `AI_PROVIDER`/`AI_MODEL` repository variables or env values. Sources: `scripts/fetch-stars.ts:10-27`, `scripts/analyze-repos.ts:37-59`, [GitHub Actions secrets docs](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets).
3. Use `permissions: contents: write` for the refresh job, keeping other permissions omitted or `none` unless later steps require them. Source: [workflow permissions docs](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions).
4. Install dependencies with the official pnpm GitHub Actions pattern and rely on frozen lockfile behavior in CI. Sources: [pnpm CI docs](https://pnpm.io/continuous-integration#github-actions), [pnpm install docs](https://pnpm.io/cli/install#--frozen-lockfile).
5. Run `pnpm run update` with step-level `GITHUB_TOKEN: ${{ secrets.STARS_GITHUB_TOKEN }}` and AI env values; do not expose the personal token to checkout or push steps. Sources: `scripts/update.ts:3-21`, `scripts/fetch-stars.ts:10-27`, [GITHUB_TOKEN docs](https://docs.github.com/en/actions/concepts/security/github_token).
6. Add a post-refresh validation/readback step that verifies `public/data/repos.json` exists, optionally checks JSON shape/counts, and runs `pnpm run typecheck`; `pnpm run update` already runs `build`. Sources: `scripts/generate-data.ts:84-100`, `package.json:7-17`, `scripts/update.ts:17-21`.
7. Stage only `data/analyzed.json` and `public/data/repos.json`, commit as `github-actions[bot]` only when tracked data changed, then push. Sources: `.gitignore:13-22`, [`actions/checkout` README](https://github.com/actions/checkout/blob/main/README.md#push-a-commit-using-the-built-in-token).
8. If branch protection blocks direct pushes, change the commit step to push an update branch and open a PR using first-party GitHub CLI/API with the same repository `GITHUB_TOKEN` or an approved GitHub App/PAT. Source: [GITHUB_TOKEN docs](https://docs.github.com/en/actions/concepts/security/github_token).

## Recommendation

Implement weekly CI refresh as a scheduled/manual GitHub Actions workflow that runs the existing `pnpm run update`, uses a user-scoped star-reading secret only for the refresh step, commits only tracked generated data with repository `GITHUB_TOKEN`, and skips commit when there is no diff. Confidence is medium-high because the repo already has the required update scripts and GitHub/pnpm provide the required CI primitives; the main uncertainty is token shape for starred repo + README access across all starred repositories, which should be resolved with one manual `workflow_dispatch` smoke run before enabling weekly automation. Sources: `scripts/update.ts:3-21`, `scripts/fetch-stars.ts:10-122`, `scripts/generate-data.ts:39-100`, [REST starring docs](https://docs.github.com/en/rest/activity/starring#list-repositories-starred-by-the-authenticated-user), [REST README docs](https://docs.github.com/en/rest/repos/contents#get-a-repository-readme), [GitHub schedule docs](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule), [`actions/checkout` README](https://github.com/actions/checkout/blob/main/README.md#push-a-commit-using-the-built-in-token).
